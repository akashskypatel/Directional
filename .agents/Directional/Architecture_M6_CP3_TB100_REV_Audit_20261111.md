## Assessment — findings, risk, and required decision

**F1 — CONFIRMED (test expectation).** Eight geometric corners is correct for the no-rail input but not for the hard-rail input under C1. Keep the plain expected set `{0,2,6,8,9,11,15,17}`; for the rail input the expected set is its union with `{1,7,10,16}`. Derive and verify that second set from *independent configured source hard-feature edges that terminate on the source boundary*. Assert that the field atlas independently classifies each such edge as `HardFeature` and prevents transport. Assert that no other hard-feature barrier is present. A mere `EXPECT_EQ(12, corners.size())` or expected set constructed from the output under test is invalid. The corrected test must fail if any required corner is missing, any extra corner appears, a hard-feature endpoint stops being a barrier, or the pass-through side-start relation changes. Preserve the original two face-row orders and the no-rail control.

**F2 — CORRECTNESS SCOPE (prior review overstates assurance if read broadly).** The product still runs only at tests and has no publication into the production pipeline. The existing 938-row gate does not test final disc stops, cut-boundary corners, or production output. RA-224 F8 explicitly limits C1 to *source-boundary* rims. The helper discards interior edges (`rimFaces[1] >= 0`); it does not solve hard-feature chaining on both sides or turning cut arcs. No O35, O36, A4, D6, Vase, or CP3 acceptance can follow from an oracle-only correction. The next-turn change must not touch producer behavior.

**F3 — EXPLICIT SEMANTICS (design risk).** The `corner` set combines actual transported field turns, undecided edge branches, and non-traversable fan barriers. It is a conservative **chain-stop** set, not necessarily a set of geometric turns or existing region side starts. Keep the name for compatibility, but state this semantic limit at the stop-set consumer. The optional atlas pointer is required for production: without it the helper cannot distinguish an authorized barrier from a missing field-transport certificate. At a future production switch, a missing required A1 certificate must be a typed failure, not an invented valid corner. The atlas itself depends on *A0 source topology region* labels; C1 is independent of later A2/A4 regions, not of all upstream region information.

**F4 — DESIGN CONFLICT: exactness debt is a required pre-switch gate.** `boundary_edge_field_branch` uses binary64 dot products, `kBoundaryAlignment=0.7`, and a `256*epsilon` ambiguity threshold (`SurfaceCellTracing.cpp:21532–21577`). The bounded-disk producer makes the matching floating-point classification independently. This can change topological chain stops on a near-tie. RA-224 calls it O39 and defers it unless a platform split appears. That deferral is not sufficient for a **certified production switch** under `DESIGN.md` Amendment 18: topology decisions require exact derivations or certified filters with exact fallback. Do not expand the CB119B test-only correction into a general exact arithmetic change. Keep O39 open and make its dedicated exact-producer+product definition and tests a mandatory condition before O36 activation; separate it into small code/build and artifact-only validation turns after the current acceptance sequence.

**F5 — FROZEN NEXT PATCH NEEDS SCOPE RECONCILIATION.** RA-224 §7 predicted `FIELD_CORNER_STOP_RECEIPT fieldCorners=8` for the hard-rail fixture; TB100 reports **12**. This prediction was explicitly not a pass condition, but it must not be repeated as an expected value. The already frozen CB120 patch contains one stop-set helper change, one factory forwarding change, a focused gate and a four-fixture census. Applying all seven touched files as one code turn is not necessary. The exact `.diff` is a historical reference; do not apply it wholesale after the corrected test without first checking its context and splitting its concerns. No production D5/D4 switch is authorized by that patch.

**F6 — PRODUCT AND CONSUMER DRIFT.** The producer's face-local best-branch rule and the new helper's copy of that rule are two owners of equivalent logic. The present test measures agreement on pass-through source rim nodes but cannot prevent a future threshold or tie-break edit in one implementation only. The production integration needs one shared authoritative decision or a published typed branch certificate consumed by both. This is **not** a CB119B task; decide it with the O39 exactness definition before a production switch.
