# `[ChatGPT Web]` Patch Application Strategy — DURABLE, DO NOT DELETE

> This file requires EXPLICIT USER AUTHORIZATION to modify or delete. Any modifications or deletions must be reverted during documentation drift audit unless explicitly approved by the user.

Historical Directional turns show a consistent empirical GitHub connector write limit of approximately 10 KB per individual write operation. Writes exceeding this size may be silently truncated without the connector returning an error. This is an observed connector behavior rather than a documented GitHub API limit.

Keep direct connector writes for genuinely minor changes when every individual content write is `<=10 KB`. Direct write remains the preferred path for an isolated small document/control change; modified workflow YAML must still satisfy `GitHub_Workflow_Policy.md` schema-validation requirements before execution.

For coherent code or documentation work that is not a genuinely minor direct write, use this standard transport and do not stage patch bytes, compressed Base64, or patch fragments in the repository:

1. **Snapshot** — obtain one exact source snapshot with `.github/workflows/agent-source-snapshot.yml` and download/verify that immutable snapshot once.
2. **Prepare + preserve locally** — edit the snapshot-derived source in the local container, generate one complete `git diff --binary --full-index --no-ext-diff` patch covering both source/code and documentation changes as applicable, verify `git apply --check` plus `git diff --check`, and emit that exact patch as a user-visible downloadable chat/File-Library backup under `RETENTION_POLICY.md`.
3. **Stage externally — file-reference transport preferred, direct Drive connector fallback** — stage the exact verified raw patch in `My Drive/Directional-CI`. Preserve its independently computed full SHA-256 and its downloadable chat/File-Library work-preservation copy. Both routes must produce a Google Drive File ID accepted by the existing `drive_apply` workflow; never modify patch bytes to work around transport failures.
   1. Ensure the patch is available as a ChatGPT conversation attachment or connector-managed file and obtain its exact `file_...` reference. Do not assume a local `/mnt/data/...` path is a usable cross-tool file reference.
   2. **Preferred:** use `files__manage_library` with `operation="upload"`, `source_file_ref={"file_id":"file_..."}`, and `destination_path="/Google Drive/Directional-CI/<exact-patch-filename>"`. Require `status="succeeded"` and extract the actual Google Drive File ID from the returned identifier. This path consumes the existing attachment by reference and avoids the active-container dependency that caused `container_session_unavailable` when `container_path` was used.
   3. **Fallback if preferred upload fails:** use `mcp__Google_Drive__search` (`item_type="folder"`) to resolve `My Drive/Directional-CI`, then `mcp__Google_Drive__upload_file` with `file_uri=<same file_ reference>`, `parent_folder_id=<resolved folder ID>`, the exact filename, and `mime_type="text/x-diff"`. Require `success=true`, `accepted_input="file_uri"`, and a nonempty Drive File ID. A connector safety-check rejection is a transport failure, not proof the patch or repository is invalid.
   4. Do **not** use `container_path` as the normal upload mechanism. It requires an active Files-visible container session, which may be unavailable even when the patch is readable locally. If no `file_...` reference exists, first make the exact patch available as a conversation/File-Library attachment; do not silently substitute a filesystem path into `upload_file`.
   5. Verify the successfully staged object with `mcp__Google_Drive__get_file_metadata`: exact filename, `text/x-diff` MIME type, expected byte size, and the intended parent folder. Metadata does **not** establish content-hash equality; the immutable patch SHA-256 and workflow-side byte verification remain mandatory.
   6. Use the resulting raw Drive File ID and independently established SHA-256 in the existing validated `drive_apply` dispatcher request. Staging is not patch application. Do not create a Google Doc, Sheet, Slide, or repository-embedded Base64 patch.

4. **Mandatory Audit** — Audit the intended changed-path set and the patch for unauthorized changes to durable documents or sections. Edits to a durable document require explicit user authorization; preserve its other durable content and record the scope of that authorization.
5. **Apply by File ID** — overwrite the retained `.agents/Directional/agent-dispatch-request.json` slot with one validated `drive_apply` request; its commit triggers durable `.github/workflows/agent-operation-dispatcher.yml` and `agent-google-drive-reusable.yml`. Pass the Drive File ID, exact patch SHA-256, exact patch base SHA, target branch, commit message, and unique request/mailbox IDs. Do not create a temporary caller or marker when the durable dispatcher is available. The reusable workflow must fetch the patch by File ID, verify full-patch and embedded diff-body hashes, verify recorded base and unchanged intended paths, run `git apply --check`, apply, run `git diff --check`, verify the exact changed-path set, commit, and push. Patch transport may not modify `.github/workflows/**`; workflow-file edits remain direct connector changes under the workflow policy.
6. **Move staged patch to trash after success** — only after the patch commit has pushed successfully, `agent-google-drive-reusable.yml` must inspect `capabilities.canTrash`. When true, move the Google Drive patch to trash using the same File ID and report `drive_file_trashed=true`; when false, skip the mutation request and report `drive_file_retirement_required=true` so the owner-authorized Drive control plane can retire it without a deterministic 403. If application/push fails, retain the Drive file and File ID for diagnosis/retry instead of retiring the only remote transport copy.
7. **Retire repository control state** — after result/log evidence and Drive retirement are verified, retain the durable dispatcher and its request slot. Only when an explicitly justified legacy temporary caller was used, delete the caller first and then its marker and other temporary control files under the normal cleanup lifecycle. Do not leave turn-specific patch payloads or fragments under `.agents/Directional/turn-payloads/`.

**Transport-failure continuation rule (same chat turn and subsequent continuation):**

- If the preferred file-reference staging route fails, diagnose the returned error and attempt the direct Google Drive connector fallback in the **same** turn. Retry a failed route only when a specific change in input, authorization, or service state justifies it; do not spin on identical deterministic failures or compromise patch checks.
- If both transport routes remain unavailable during the same chat turn, **preserve the exact verified patch** as a user-visible conversation/File-Library attachment, record its filename, full SHA-256, embedded base/diff-body hashes, intended paths, staging attempts/errors, and current repository authority. Do not claim any patch was applied or mark the turn `BLOCKED` merely because file staging/transferring failed.
- Close that chat turn with repository-root `STATUS: IN_PROGRESS` (same `Turn`, same original `Started at`, latest `Resumed at` if applicable, and empty `Ended at`) and the normal machine-readable status footer. **On the next continuation turn, preserve the same turn ID and original start timestamp, update `Resumed at`, and retry the patch-application transport from the preserved verified patch before re-deriving or editing work.** Resume subsequent patch application and close as `COMPLETE` only after full validation, committed changes, required cleanup, and final beacon.
- Do not convert a genuine independent design/architecture/review/authority stop condition into an `IN_PROGRESS` transport yield. Such conditions remain governed by the normal stop/blocker rules. This exception concerns recoverable same-turn patch transport failures only.

Before any remote application, resolve current branch authority. If the branch advanced after the patch base, the reusable workflow must fail closed when any intended path changed; reconstruct/rebase the patch deliberately rather than force-pushing or applying blindly.
